# 🚇 Moscow Metro ML: прогноз пассажиропотока и поиск аномалий на открытых данных Москвы

Pet-проект ML-инженера: сквозной пайплайн от **API Портала открытых данных Правительства Москвы**
(data.mos.ru) до REST API. Пайплайн:

1. **Прогнозирует** входы пассажиров на каждой станции метро на следующий квартал.
2. **Находит аномалии** и **объясняет** их: закрыта ли станция, просела ли вся линия или весь город.
3. **Отличает реальные события от ошибок в данных** сверкой трёх независимых наборов.

Все данные реальные, синтетики нет.

| Набор data.mos.ru | ID | Что внутри |
|---|---|---|
| Пассажиропоток по станциям Московского метрополитена | 62743 | ~315 станций × 22 квартала (2021Q1–2026Q2), входы и выходы |
| Месячный пассажиропоток по видам транспорта | 62521 | метро, МЦК, автобус, трамвай, электробус, троллейбус; 2019–2026 |
| Годовой пассажиропоток по видам транспорта | 62523 | годовые итоги для сверки |

## 1. Что нашлось в реальных данных

Ещё до моделирования проверки качества (`src/quality.py`) нашли в данных проблемы, которые не видны,
если смотреть на одну таблицу:

| Проблема | Как найдена | Что с ней делаем |
|---|---|---|
| **595 точных дублей** (9.2% строк) | ключ «станция + линия + год + квартал» | удаляем; конфликтные дубли (разные значения) обрабатываются отдельно: остаётся последняя версия по `global_id` |
| **167 станций-кварталов с нулевым потоком** | вход или выход = 0 | это не ошибка, а закрытие станции на ремонт: флаг `is_closed`, такие кварталы не используются как цель обучения |
| **5 неполных кварталов** (2021Q3, 2023Q2, 2024Q4, 2025Q3, 2025Q4) | сумма по станциям покрывает только **42–87%** месячного итога метро | недостающие станции считаются пропусками, а не «падением потока» |
| **Ошибка ввода: январь 2025** | метро в январе 2025 = **17.3 млн** вместо ~172 млн (потерян разряд). Сумма месяцев за 2025 г. на 6.8% меньше годового итога, а станционные данные дают 121% месячного итога | детектор помечает месяц как `data_error`, а не как падение спроса |
| **Прекращённый ряд «Троллейбус»** | значения ≈ 0 после 2022 г. | исключён из городского детектора |
| **269 станций с разрывами рядов** | следствие неполных кварталов | признаки допускают пропуски (NaN + маски), якорь прогноза выбирается из доступных лагов |

## 2. Идея детекции аномалий: «что произошло и где»

Аномалия — это сильное отклонение факта от прогноза, построенного **только по прошлому**. На квартальных
данных важно ещё и **объяснить** отклонение, поэтому оно раскладывается по иерархии:

```
r       = log(факт / прогноз)                     отклонение станции от ожидания
r_city  = медиана r по всем станциям квартала      весь город (неполные данные, общий спад)
r_line  = медиана (r − r_city) по станциям линии   вся линия (закрытие участка, новая линия рядом)
r_rel   = r − r_city − r_line                      отклонение именно этой станции
imb     = log(вход/выход) − обычный для станции    дисбаланс учёта
```

Затем считаются робастные z-score (медиана/MAD устойчивы к самим аномалиям). Чтобы тревога поднялась,
отклонение должно быть и статистически значимым, и практически заметным (станция ±20%, линия ±7%,
вход/выход ±10%). Isolation Forest даёт второе мнение для уровня серьёзности.

| Тип | Что означает |
|---|---|
| `closure` | нулевой поток: станция закрыта |
| `partial_closure` | факт < 25% прогноза: закрыт вестибюль или станция работала часть квартала |
| `station_drop` / `station_surge` | станция отклонилась сильнее, чем её линия и город |
| `line_event` | изменилась вся линия (одно событие вместо десятка станционных тревог) |
| `imbalance` | соотношение «вход/выход» не такое, как обычно на станции (сбой учёта, односторонний вестибюль) |
| city event | весь город за квартал отклонился от прогноза (2025Q1: **−12%**) |

**Зачем иерархия.** В 2025Q1 весь город оказался на 12% ниже прогноза. Иерархический детектор выделяет это
как **одно городское событие** и отдельно перечисляет 73 станции, которые выбиваются уже из общего фона.
Детектор без контекста калибрует порог по «сырым» отклонениям, в которые входят общегородские сдвиги.
Его шкала шире, и он хуже видит проблемы отдельных станций (в 2025Q1 нашёл 46 станций против 73 у
иерархического). Ещё он не может сказать, что сдвинулась вся линия, а не каждая её станция по отдельности
(см. таблицу ниже).

**Городской уровень и атрибуция «событие или ошибка».** `CityMonthlyDetector` строит для месячных рядов
сезонный профиль и уровень (медиана трёх прошлых месяцев) и оценивает отклонение через z-score. Он нашёл
41 аномалию. 40 из них приходятся на март 2020 — апрель 2021 (локдаун и восстановление после него).
Январь 2025 подписан как **ошибка данных**, потому что не сходится ни с годовым итогом, ни со станционными
данными.

**Как оценить без разметки.** Меток аномалий в реальных данных нет. Поэтому в реальный test-период
**вставляются** контролируемые аномалии: падение и рост отдельных станций, сдвиг целой линии, дисбаланс.
Так известно, где они должны быть найдены (`evaluate_by_injection`, 10 раундов).

| Детектор (test, инъекция) | precision | recall | ложные тревоги | событие линии найдено / тип определён |
|---|---|---|---|---|
| **с иерархией город → линия → станция** | 0.942 | **1.000** | 0.8% | **1.00 / 1.00** |
| без контекста | 1.000 | 0.975 | 0.0% | 0.92 / **0.00** |

Без контекста детектор чуть точнее, но не может сказать, что изменилась вся линия: каждую её станцию он
помечает как отдельное падение. Ради этой информации иерархия и нужна.

## 3. Прогноз

* **Задача:** входы станции в квартале *t* по кварталам ≤ *t−1*. Используется одна глобальная модель на
  все станции, потому что ряды короткие (≤22 точек) и с дырами.
* **Якорь и цель.** Модель предсказывает `log(факт) − log(якорь)`, то есть относительное изменение.
  Якорь — тот же квартал год назад (сезонность), а если его нет, прошлый квартал.
* **Признаки.** Лаги 1–5 относительно якоря с масками пропусков, годовой тренд станции, тренд линии и
  города, квартал года, «возраст» станции, флаг МЦК.
* **Модели.** Градиентный бустинг `HistGradientBoosting` (нативные NaN, L1-loss) и **MLP на PyTorch** с
  embedding'ами станции и линии (Huber-loss, early stopping по val).
* **Разбиение по времени:** train — цели до 2024Q2, val — 2024Q3–2025Q2, test — 2025Q3–2026Q2.
  Champion выбирается **по val**, test используется только для отчёта.
* **Production refit.** После выбора та же конфигурация дообучается на всех данных с числом итераций,
  найденным по val, и строит прогноз на **2026Q3** для 295 станций. Интервал — 10-й и 90-й перцентили
  ошибок на val.

### Результаты (WAPE, ниже — лучше)

| Модель | val WAPE | test WAPE |
|---|---|---|
| Бейзлайн: прошлый квартал | 0.133 | **0.070** |
| Бейзлайн: тот же квартал год назад | 0.088 | 0.096 |
| Бейзлайн: год назад × годовой тренд | 0.119 | 0.199 |
| GBM | 0.087 | 0.072 |
| **PyTorch MLP (champion, v1)** | **0.073** | 0.076 |
| PyTorch MLP wide (sweep, v2: не повышена) | 0.073 | 0.080 |

Ещё одна метрика: на test **без** кварталов, помеченных как аномалии, WAPE champion'а составляет **0.067**.
Значит, заметная часть ошибки — это реальные события (закрытия, перераспределение потока), а не ошибки модели.

**Честный разбор.** На test наивный бейзлайн «как в прошлом квартале» лучше всех (0.070), а на val он
худший (0.133). Модель выбрана по val, и это правильно: выбирать по test — значит подглядывать в будущее.
Разброс бейзлайнов между периодами показывает, насколько нестабильны квартальные данные (неполные
публикации, перераспределение потока после открытия БКЛ и Троицкой линии). Модель устойчивее: 0.073 / 0.076.
Хороший вопрос для собеседования: «Что бы вы сделали?» Например, rolling-origin оценка по нескольким
периодам и ансамбль модели с наивным прогнозом.

**Champion / challenger.** Новая версия становится `champion` только при улучшении val WAPE минимум на 1%.
В sweep лучшей по val оказалась v2 (0.0732 против 0.0733). Это шум, и v2 не была повышена. Её test WAPE
действительно хуже (0.080 против 0.076).

## 4. Архитектура

```

                                       │ --to-postgres
                                       ▼
                         PostgreSQL: посадочная зона *_raw (без UNIQUE)
                                       ▼
          src/data_loader.py: очистка (Pandas, тот же шаг на PySpark) ──► parquet
                                       ▼
          src/quality.py: сверка станции ↔ месяцы ↔ годы, DQ-отчёт, ворота качества
                                       ▼
          src/features.py: панель станция × квартал, признаки только из прошлого
                                       ▼
   бейзлайны · GBM · PyTorch MLP ──► выбор по val ──► детекторы аномалий ──► refit на всех данных
                                       ▼
          MLflow: параметры, кривые обучения, метрики, артефакты, Model Registry (алиас champion)
                                       ▼
          artifacts/latest (бандл) ──► FastAPI (Docker)        Airflow: @monthly fetch → … → register
```

## 6. Запуск

### Локально
```bash
python -m venv .venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                   # впишите MOS_API_KEY (ключ из личного кабинета apidata.mos.ru)

python -m src.ingest                                   # скачать 3 набора в data/raw (~10 секунд)
python -m src.training --stage all                     # очистка → DQ → бейзлайны → модели → детекторы → MLflow
python -m src.training --stage sweep                   # перебор гиперпараметров (champion/challenger)
mlflow ui --backend-store-uri sqlite:///mlflow.db      # http://localhost:5000
uvicorn api.main:app --reload                          # http://localhost:8000/docs
python -m pytest -q
```

### Docker
```bash
docker compose up -d postgres mlflow
docker compose --profile jobs run --rm pipeline        # API → PostgreSQL → Spark → обучение
docker compose up -d api
```

## 8. Масштабирование

* **Данные.** Сейчас это агрегаты (тысячи строк), поэтому локально хватает Pandas. В ДИТ реальный
  источник — события валидаторов, миллиарды строк. Тот же шаг очистки уже написан на PySpark: меняются
  только `SPARK_MASTER` (YARN/K8s) и источник (JDBC/parquet в S3). Ключевые приёмы: `row_number()` для
  дублей и broadcast-join'ы справочников.
* **Модель.** Одна глобальная модель на все станции. Новая станция получает OOV-embedding и работает по
  лагам, а не требует новой модели.
* **Сервис.** API не хранит состояния: модель загружается один раз при старте, сервис масштабируется
  репликами за балансировщиком. Прогнозы на следующий квартал считаются батчем заранее. Отдельный
  образ для API без Java и PySpark будет в разы меньше.
* **MLOps.** Версии наборов данных записываются в метаданные модели (lineage). Ворота качества стоят до
  обучения. Champion/challenger работает с порогом улучшения. Переобучение запускается по расписанию
  Airflow, откат делается переключением алиаса в Model Registry.

## 9. Ограничения и идеи развития

* Квартальная детализация не позволяет ловить аномалии в реальном времени. Следующий шаг — суточные
  данные валидаторов (в ДИТ они есть), тогда та же иерархия город → линия → станция работает по дням.
* Короткая история: оценка на одном val-периоде шумная. Стоит добавить rolling-origin CV и ансамбль
  с наивным прогнозом.
* Контекст для подписей городских аномалий (COVID-19) задан вручную. Можно подключить календарь событий:
  открытия станций, закрытия участков, массовые мероприятия.
* Станция, перенесённая на другую линию (Некрасовская → БКЛ), начинает новый ряд. Можно добавить
  справочник переименований.
